---
title: "Bucket Replication"
description: "Set up one-way and bidirectional bucket replication between MinIO clusters, manage replication rules, and monitor replication status."
---

Bucket replication continuously synchronizes selected objects from a source bucket to one or more destination buckets, which can reside on the same cluster or a different cluster. MinIO's replication implementation is based on the AWS S3 Replication V2 configuration with MinIO-specific extensions for delete replication, replica modification sync, and existing object replication.

## Prerequisites

Before configuring replication:

- Both source and destination buckets must have **versioning enabled**.
- If object locking is required, both buckets must have been created with `mc mb --with-lock`.
- The user configuring replication on the **source** needs `s3:GetReplicationConfiguration`, `s3:PutReplicationConfiguration`, and `admin:SetBucketTarget` permissions.
- The user credentials used on the **destination** need `s3:ReplicateObject` and related permissions.

<Tip>
  Do not run replication using root credentials. Create dedicated users with only the permissions required for replication.
</Tip>

### Minimum IAM policy — source admin

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Action": ["admin:SetBucketTarget", "admin:GetBucketTarget"],
      "Effect": "Allow",
      "Sid": ""
    },
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetReplicationConfiguration",
        "s3:PutReplicationConfiguration",
        "s3:ListBucket",
        "s3:ListBucketMultipartUploads",
        "s3:GetBucketLocation",
        "s3:GetBucketVersioning"
      ],
      "Resource": ["arn:aws:s3:::srcbucket"]
    }
  ]
}
```

### Minimum IAM policy — destination user

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetReplicationConfiguration",
        "s3:ListBucket",
        "s3:GetBucketLocation",
        "s3:GetBucketVersioning",
        "s3:GetBucketObjectLockConfiguration"
      ],
      "Resource": ["arn:aws:s3:::destbucket"]
    },
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetReplicationConfiguration",
        "s3:ReplicateTags",
        "s3:AbortMultipartUpload",
        "s3:GetObject",
        "s3:GetObjectVersion",
        "s3:GetObjectVersionTagging",
        "s3:PutObject",
        "s3:DeleteObject",
        "s3:ReplicateObject",
        "s3:ReplicateDelete"
      ],
      "Resource": ["arn:aws:s3:::destbucket/*"]
    }
  ]
}
```

## Setting up one-way (active-passive) replication

<Steps>
  <Step title="Create users on both clusters">
    On the source cluster, create a replication admin user and attach the source policy:

    ```sh
    mc admin user add source repladmin repladmin123
    mc admin policy create source repladmin-policy ./repladmin-policy-source.json
    mc admin policy attach source repladmin-policy --user=repladmin
    ```

    On the destination cluster, create a replication user and attach the destination policy:

    ```sh
    mc admin user add dest repluser repluser123
    mc admin policy create dest replpolicy ./replpolicy.json
    mc admin policy attach dest replpolicy --user=repluser
    ```
  </Step>
  <Step title="Enable versioning on both buckets">
    ```sh
    mc version enable source/bucket
    mc version enable dest/bucket
    ```
  </Step>
  <Step title="Add a replication rule">
    ```sh
    mc replicate add source/bucket \
      --priority 1 \
      --remote-bucket http://repluser:repluser123@dest-endpoint:9000/bucket \
      --replicate existing-objects,delete,delete-marker,replica-metadata-sync
    ```

    Output:
    ```
    Replication configuration applied successfully to source/bucket.
    ```
  </Step>
</Steps>

<Note>
  For `mc` versions at or after `RELEASE.2022-12-24T15-21-38Z`, the `--remote-bucket` flag takes a full URL of the form `https://accessKey:secretKey@replica-endpoint:9000/destbucket`. Older versions require an ARN generated by `mc admin bucket remote add`.
</Note>

## Setting up two-way (active-active) replication

To make replication bidirectional, repeat the replication setup from the destination pointing back at the source. MinIO's **replica modification sync** (enabled by default) ensures that metadata changes on a replica object are propagated back to the source.

```sh
# Configure replication from dest → source
mc replicate add dest/bucket \
  --priority 1 \
  --remote-bucket http://repladmin:repladmin123@source-endpoint:9000/bucket \
  --replicate existing-objects,delete,delete-marker,replica-metadata-sync
```

<Warning>
  In active-active replication with delete marker replication enabled, concurrent deletes on both clusters can produce duplicate delete markers. Plan your replication topology carefully to avoid this scenario.
</Warning>

## Replication rules with filters

Replication rules can be scoped by object prefix and/or tags to limit which objects are replicated.

### Filter by prefix and tags

```sh
mc replicate add myminio/srcbucket \
  --priority 1 \
  --remote-bucket https://accessKey:secretKey@replica-endpoint:9000/destbucket \
  --tags "Year=2019&Company=AcmeCorp" \
  --storage-class "STANDARD" \
  --replicate "delete,delete-marker"
```

The generated replication configuration:

```json
{
  "Role": "",
  "Rules": [
    {
      "Status": "Enabled",
      "Priority": 1,
      "DeleteMarkerReplication": { "Status": "Enabled" },
      "DeleteReplication": { "Status": "Enabled" },
      "Filter": {
        "And": {
          "Prefix": "Tax",
          "Tags": [
            { "Key": "Year", "Value": "2019" },
            { "Key": "Company", "Value": "AcmeCorp" }
          ]
        }
      },
      "Destination": {
        "Bucket": "arn:minio:replication::...:destbucket",
        "StorageClass": "STANDARD"
      },
      "SourceSelectionCriteria": {
        "ReplicaModifications": { "Status": "Enabled" }
      }
    }
  ]
}
```

<Warning>
  Delete marker replication is disallowed when the replication rule uses tag filters. This matches AWS S3 behavior.
</Warning>

## Priority and bandwidth configuration

When multiple replication rules match an object, the rule with the **highest priority number** takes effect.

To limit network bandwidth consumed by replication, and to configure synchronous replication or health-check intervals:

```sh
mc admin bucket remote add myminio/srcbucket \
  https://accessKey:secretKey@replica-endpoint:9000/destbucket \
  --service replication \
  --region us-east-1 \
  --sync \
  --healthcheck-seconds 100
```

To tune the number of concurrent replication workers (default: 100):

```sh
mc admin config set myminio api replication_workers=50
```

## Replication status monitoring

Replication status is embedded in object metadata:

| Status | Location | Meaning |
|---|---|---|
| `PENDING` | Source | Object is queued for replication |
| `COMPLETED` | Source | Replication succeeded on all targets |
| `FAILED` | Source | Replication failed; will be retried |
| `REPLICA` | Destination | Object was written by replication |

All replication failures are automatically retried during the periodic disk scanner cycle, which runs approximately every minute and scans up to 1/16 of the namespace per pass.

### Inspecting status via mc stat

```sh
mc stat myminio/srcbucket/myobject
```

The output includes `X-Amz-Replication-Status` metadata showing the current replication state.

### Monitoring delete marker replication

```sh
mc stat --version-id <dm-version-id> myminio/srcbucket/myobject
```

This returns `X-Minio-Replication-DeleteMarker-Status` for the delete marker version.

### Watching events via notifications

Configure notifications on the source bucket to capture replication events:

```sh
mc event add myminio/srcbucket <arn> \
  --event s3:Replication:OperationCompletedReplication,s3:Replication:OperationFailedReplication
```

## Existing object replication

To replicate objects that existed before the replication configuration was added, enable existing object replication with the `existing-objects` flag:

```sh
mc replicate add myminio/srcbucket \
  --priority 1 \
  --remote-bucket https://accessKey:secretKey@replica-endpoint:9000/destbucket \
  --replicate "existing-objects,delete,delete-marker,replica-metadata-sync"
```

### Re-syncing after a DR site is lost

If a destination site is fully lost, trigger a full re-sync:

```sh
mc replicate resync start myminio/srcbucket --remote-bucket <arn>
```

Monitor progress:

```sh
mc replicate resync status myminio/srcbucket --remote-bucket <arn>
```

## Managing replication rules

```sh
# View current replication configuration
mc replicate export myminio/srcbucket

# List replication rules
mc replicate ls myminio/srcbucket

# Edit a specific rule (e.g., disable replica metadata sync)
mc replicate edit myminio/srcbucket --id <rule-id> \
  --replicate "delete,delete-marker"

# Re-enable replica metadata sync
mc replicate edit myminio/srcbucket --id <rule-id> \
  --replicate "delete,delete-marker,replica-metadata-sync"
```

## mc replicate command reference

| Command | Description |
|---|---|
| `mc replicate add <alias>/<bucket> --remote-bucket <url>` | Add a replication rule |
| `mc replicate ls <alias>/<bucket>` | List replication rules |
| `mc replicate edit <alias>/<bucket> --id <id>` | Edit a replication rule |
| `mc replicate export <alias>/<bucket>` | Export replication config as JSON |
| `mc replicate resync start <alias>/<bucket>` | Trigger full re-sync to a target |
| `mc replicate resync status <alias>/<bucket>` | Check re-sync progress |
